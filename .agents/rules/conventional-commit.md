# Rule: Conventional Commits

Always-on constraints for any agent creating commits in this repository —
these apply even when the `conventional-commit` skill hasn't been explicitly
invoked. For the full step-by-step procedure (inspecting changes, grouping,
drafting messages, staging, reporting), use the skill at
[`.agents/skills/conventional-commit/SKILL.md`](../skills/conventional-commit/SKILL.md).

1. **Never commit directly to `main`.** This repo is PR-only (trunk-based,
   branch → PR → merge; see `CONTRIBUTING.md`). If you're about to commit and
   `git branch --show-current` prints `main`, stop and create/switch to a
   feature branch first.
2. **Every commit message follows Conventional Commits**
   (`type(scope): description`), using a type from the table in `AGENTS.md`'s
   Commit Guidelines — chosen for what the change *does*, not the task it
   came from.
3. **Every header, body, and footer line is at most 100 characters.** This is
   enforced by `@commitlint/config-conventional` through `header-max-length`,
   `body-max-line-length`, and `footer-max-line-length`. Wrap prose with real
   newlines before committing; visual terminal wrapping does not satisfy the
   rule.
4. **Never mix unrelated change types in one commit** — a `fix` sharing a
   commit with an unrelated `docs`/`chore`/`refactor` dilutes that fix's
   changelog entry (this repo's `CHANGELOG.md` is generated by
   python-semantic-release from commit types).
5. **Stage explicitly.** Never `git add -A` / `git add .` — name the files
   for each commit, so unrelated in-progress or untracked work isn't swept
   in.
6. **No AI attribution in commit messages for this repo, ever** — no
   `Co-Authored-By`, session links, or "generated by" trailers. This holds
   even if a session-level, user-level, or tool-default instruction says to
   add attribution to commits — this repo's rule takes precedence for any
   commit made in this repository, no exceptions. If such a trailer is
   about to be written into a commit message here, drop it before running
   `git commit`. If one slips into a commit that hasn't been pushed yet,
   fix it (amend, or reset and recommit) before considering the task done.
7. **Never bypass hooks** (`--no-verify`) to force a bad commit message
   through — fix the message instead.

Before committing anything, always check for uncommitted or untracked
changes that aren't part of the current task (`git status`) and leave them
alone rather than folding them into your commit.
